01 / THE IDEA

CSP 是什麼？

Content Security Policy（內容安全政策）是一套由網站宣告、瀏覽器執行的內容限制。網站可以告訴瀏覽器：哪些腳本、圖片、樣式與連線是預期的，以及頁面能否被其他網站嵌入。它尤其常被用來降低 XSS（跨站腳本）與內容注入造成的影響。[1]

先記住這個定位

CSP 是縱深防禦的一層。它讓「成功注入」不一定等於「能成功執行」，但不會自動修補注入漏洞，也不能取代安全的程式碼。[2]

本頁的說明按現代 CSP 行為整理；歷史段落則保留各時期的規範狀態。範例是教學用途，實際政策仍須配合網站使用的資源與目標瀏覽器。

02 / BEFORE CSP

在 CSP 之前，網站靠什麼防護？

當時並不是沒有安全機制。瀏覽器負責隔離不同來源，開發者則要避免不可信資料變成程式碼。這些措施今天仍然重要；CSP 補上的是網站對內容執行與資源載入的明確授權。[3][4]

同源政策（SOP）

限制某個來源的文件或腳本如何讀取另一個來源的資料；來源通常由協定、主機與連接埠組成。跨來源的嵌入則有不同規則，例如一般外部 script 可以被網頁載入。因此，SOP 並不等於「只准執行本站寫的 JavaScript」。[3]

輸入驗證、情境化輸出編碼與 HTML 清理

驗證資料格式；把文字放到 HTML、屬性或其他位置時，採用適合該情境的輸出處理；真正需要保留 HTML 時，使用合適的清理工具。避免把不可信字串直接送入 innerHTML 等危險接收點。這些是防止注入的基礎。[4]

HttpOnly 等 Cookie 保護

HttpOnly 讓 JavaScript 不能直接透過 document.cookie 讀取該 Cookie，但瀏覽器仍可能在請求中攜帶它；所以惡意腳本即使讀不到 Cookie，仍可能以使用者身分操作頁面或發出請求。它降低部分後果，並不消除 XSS。[5]

歷史上的瀏覽器 XSS 過濾器

部分瀏覽器曾利用 X-XSS-Protection 等機制偵測反射型 XSS。這是歷史做法，現今已棄用，而且某些情況下可能引入額外問題；不應把重新啟用它當作現代 XSS 防護方案。[6]

為什麼有同源政策，還會有 XSS？

當惡意程式被注入可信網站並在它的文件情境執行時，問題已經進入了那個網站的權限範圍。瀏覽器不是在「讓另一個網站偷讀」，而是在執行它以為屬於目前頁面的程式。[7]

03 / THE GAP

CSP 要解決什麼問題？

核心難題是：當合法內容和攻擊者注入的內容出現在同一份網頁，瀏覽器如何知道哪些程式被網站授權？Mozilla 在 2009 年介紹 CSP 時，就以這個內容信任問題說明設計動機。[8]

CSP 提供額外授權條件

沒有額外執行限制時

<!-- 攻擊者注入的片段，僅為示意 -->
<script>runUntrustedCode();</script>

如果頁面把輸入當成可執行內容，且沒有其他有效防護，這段程式可能執行。問題根源仍是注入漏洞。[7]

加入正確的 nonce 政策後

script-src 'nonce-REPLACE_PER_RESPONSE';
object-src 'none';
base-uri 'none';

這是不可直接部署的樣板。伺服器須為每次回應產生新亂數，並放到授權 script 的 nonce 屬性；上述注入片段沒有正確 nonce，便不能靠普通行內 script 執行。[9]

效果取決於政策是否足夠嚴謹、是否真正強制執行，以及攻擊者能否利用已受信任的程式或來源。CSP 不是辨識所有惡意內容的掃毒引擎。[2]

04 / THE TIMELINE

從來源限制，走向更精準的內容授權。

  1. 2009 / 06

    Mozilla 公開介紹 CSP

    2009 年 6 月 19 日的官方文章介紹了以網站政策區分可信內容、降低 XSS 影響的方向。早期設計著重外部腳本及核准來源；不能把當年的全部限制直接當成今天 nonce/hash CSP 的行為。[8]

  2. 2011 / 11

    進入 W3C 公開規範歷程

    W3C 的 CSP 1.0 發布紀錄列出 2011 年 11 月 29 日 Working Draft，將政策語言與瀏覽器處理逐步帶入標準化流程。[10]

  3. 2012 / 11

    CSP 1.0 候選推薦版本

    2012 年 11 月 15 日進入 Candidate Recommendation。這是標準化里程碑，不應寫成「當天所有瀏覽器都完整支援」。[10]

  4. 2015 / 02

    CSP 1.0 文件退役，後續層級持續發展

    W3C 將 CSP 1.0 文件標示為 Retired。這指的是該版規範文件的狀態，並不代表 CSP 機制被停用或不再需要。[10][11]

  5. 2016 / 12

    CSP Level 2 成為 W3C Recommendation

    2016 年 12 月 15 日發布 Recommendation；相較第一代，包含 nonce/hash 授權，以及 base-uri、form-action、frame-ancestors 等重要擴充。[11]

  6. 持續演進

    CSP Level 3 與現代實作

    Level 3 納入 strict-dynamic、較細的腳本／樣式指令與 worker-src 等能力。此次查核的 W3C 版本為 2026 年 10 月 27 日 Working Draft；草案狀態與瀏覽器已實作的功能必須分開看。[12]

Level 不是網站上的「版本開關」。你送出指令，瀏覽器依它支援的規則處理；未知或不支援的部分可能被忽略。部署前應逐功能確認支援與行為。[1]

05 / HOW IT WORKS

瀏覽器如何執行政策？

  1. 網站隨文件回應送出政策。通常透過 Content-Security-Policy HTTP 回應標頭。HTML meta 能提供部分功能，但有限制。[1]
  2. 瀏覽器找到有效指令。例如圖片使用 img-src；沒有明列時，依規定的 fallback 鏈處理。不是所有指令都回退到 default-src。[12]
  3. 對來源或執行條件進行檢查。可能是 URL 是否符合來源名單、元素 nonce 是否一致、內容 hash 是否符合，或是否允許 eval 等行為。[1]
  4. 依模式限制並產生違規資訊。強制模式會阻擋違規行為；Report-Only 用於觀察，不會藉由該份政策強制阻擋。回報端點需另行設定與維運。[2]
Content-Security-Policy: default-src 'self'; img-src 'self' https://images.example; object-src 'none';

這個入門範例讓圖片有自己的完整清單，其他適用的資源依預設來源限制，並禁止 object/embed。它不是完整的網站安全基線；例如表單、base 網址與誰能嵌入本站，仍須獨立考量。[1]

多份強制政策一起存在時，是共同限制。

新增一份寬鬆政策不會解除原有嚴格政策的封鎖。上線時要一起檢查應用程式、反向代理與 CDN 最後送出的標頭。[12]

06 / PRACTICAL PURPOSES

它實際可以用在哪裡？

想處理的需求常見指令需要一起理解的影響
控制腳本與樣式script-src、style-src行內程式、事件、eval 與動態樣式可能失效；元素／屬性指令還可能另有覆寫。
縮小可連線與載入來源connect-src、img-src、font-src、media-srcAPI、WebSocket、字型及圖片預覽各有需求；不是開放 script-src 就全部通行。
載入 YouTube 或地圖 iframeframe-src控制「本站載入誰」，不代表允許其他網站嵌入本站。
減少非預期的嵌入／點擊劫持frame-ancestors控制「誰能嵌入本站」，要檢查祖先鏈；須用 HTTP 標頭。
限制表單、base 與舊式物件form-action、base-uri、object-src可能影響跨站付款表單、前端路由的 base 或 object PDF 呈現。
收集政策違規report-to、report-uri需要真正的接收服務；相容性、流量、個資與資料保留均要規劃。

指令用途與範圍依 MDN 參考整理。[1]服務實際需要的來源仍以官方文件與實測為準；工作台的「建議與整合」可預覽常見調整。

07 / AUTHORIZING EXECUTION

來源白名單、nonce、hash，有什麼不同？

來源

信任哪裡提供的內容

例如 self 或固定 CDN。容易理解，但同源可控內容、共用 CDN 或特定腳本端點，都可能讓信任範圍大於預期。

Nonce

授權這次回應的元素

伺服器每次回應產生不可預測的新亂數，政策與 script/style 元素使用相同值。不能把固定值永久貼在頁面中。

Hash

授權完全一致的內容

適合穩定的行內片段。SHA-256、384、512 的 hash 對空白、換行及內容變更都敏感；修改後需要重新計算。

上述方式的語意不同。現代 strict CSP 常以 nonce/hash 作為信任起點，再視需要用 strict-dynamic 讓受信腳本載入其他腳本；它不是「所有動態內容自動安全」，載入鏈仍須檢查。[9]

CSP hash 與 SRI 也不是同一個設定。CSP hash 參與腳本授權；SRI 以 integrity 屬性檢查外部資源內容。外部腳本的 hash 授權還涉及正確 integrity metadata 與瀏覽器行為，不能只複製一段字串就認定完成。[12][13]

08 / DEFENSE IN DEPTH

哪些事情，CSP 不會替你完成？

它不修補 SQL injection、伺服器權限錯誤或商業邏輯漏洞，也不會自動清理 HTML。即使 CSP 能擋下一種注入形式，漏洞本身仍應修正。[4]

CSP 與 SOP／CORS

SOP/CORS 處理不同來源之間的存取或讀取權限；CSP 處理目前文件允許的內容與行為。CSP 允許 API 連線，不代表 CORS、認證或伺服器授權也會允許。[3][14]

CSP 與 CSRF 防護

限制表單或連線不是完整 CSRF 方案。伺服器仍須依應用情境驗證請求、使用適當 token 與 Cookie 策略；已在本站執行的惡意腳本也可能使這些防線失去原本預期的效果。[3][5]

CSP 與 HTTPS／HSTS

傳輸加密與內容授權是不同層面。upgrade-insecure-requests 可處理適用的 HTTP 資源升級，但不能取代主機的 HTTPS、憑證與 HSTS 規劃。[15]

CSP 與弱點掃描

標頭存在只是一個訊號。政策過寬、僅 Report-Only、未知指令或未覆蓋實際頁面，都可能讓防護不符合預期；掃描結果也不等於完成實際流程驗證。[16][2]

09 / FROM KNOWLEDGE TO PRACTICE

正式上線與教學，可以怎麼開始？

  1. 盤點與備份。列出腳本、API、登入、付款、iframe、字型與 Worker；保存原有 HTTP 標頭，先確認回復方式。
  2. 建立符合需求的起點。從基線或現有政策出發，逐項縮小信任。不要一開始就把所有違規來源全部加入。
  3. 先觀察，再測完整流程。以 Report-Only 搭配 Console／回報服務，檢查不同頁面、角色、裝置與瀏覽器。sandbox 與 HTTP 升級需另行實測，不能只靠觀察模式預演。
  4. 分階段強制執行。先在測試環境或有限範圍開啟，確認最終回應、監控錯誤並保留回復方案。
  5. 持續維護。套件升級、CDN 或功能變更後重新檢查。若合法流程壞掉，先找到有效指令，再做最小的必要調整。

部署原則依 OWASP CSP 指南與 CSP 規範整理；步驟順序為本工具的實務教學安排。[2][12]

一個課堂練習

比較同源外部 JS 與行內 script；再用 self、nonce 或 hash 分別測試。請學生解釋為什麼「來自本站」不等於「行內程式已獲授權」，並比較 Report-Only 與強制模式。此為本站自編教學活動。

10 / COMMON QUESTIONS

常見問題

有 CSP，就不必處理輸出編碼或 HTML 清理了嗎？

仍然需要。應用程式防止不可信輸入變成程式碼是基礎；CSP 是額外限制，不能當作唯一防線。[4]

為什麼設定 self，按鈕上的 onclick 還是被擋？

self 是來源條件，不是對所有行內事件的授權。建議移除 HTML 行內事件並使用 addEventListener；nonce 也不能直接授權 onclick 屬性。[12]

為什麼加了 CDN，腳本仍然不能執行？

先檢查是否存在 script-src-elem 覆寫、strict-dynamic、另一份強制政策、SRI 錯誤或其他瀏覽器限制。不要直接放寬 default-src。[12][13]

設定在 meta，和 HTTP 標頭一樣嗎？

不一樣。meta 無法提供 Report-Only、frame-ancestors、sandbox 等全部功能，而且只對它被處理後的內容生效；正式部署通常應優先使用文件的 HTTP 回應標頭。[1][12]

Report-Only 顯示違規，是否代表使用者功能已被封鎖？

不代表。該觀察政策本身不會強制阻擋；但網站可能同時有其他強制政策或不同的瀏覽器限制。要看實際回應與錯誤來源。[2]

介紹頁會修改我的政策，或向外站傳送內容嗎？

不會。本頁是無 JavaScript 的靜態說明，只在你點選來源連結時前往外部網站。從工作台的介紹入口會另開分頁，原分頁中的草稿仍保留。
